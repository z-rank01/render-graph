# 恢复 Render Graph pass culling 与 transient 资源惰性分配
## 背景与依据
当前 `compile_graph` 八 phase 无 culling：所有声明的 pass 进调度、所有声明的资源（即使无人使用）都在
`compile_lifetimes` 获得物理条目（`system.cpp:564-604` 与 `:608-648` 的 else 分支无条件 push
`physical_*_meta` + memory block），backend 随之做真实 VMA 分配。最初设计（`d0f0a3f` system.h 的
Step D）以 declared outputs 为根反向标记活跃 pass。本次恢复该语义，并顺势让 transient 资源恢复
"culling 之后才物化"的惰性。
代码事实（已核实）：
- `compile_synchronization`（`system.cpp:669`）与 `compile_submissions`（`:805`）均按
  `plan.scheduled_passes` 遍历，同步内层再按 `event.pass` 过滤——只要 `scheduled_passes` 只含活跃
  pass，这两个 phase 无需改动。
- `compile_lifetimes` 按 `state.accesses` 全量事件统计，需要按活跃集过滤；物理条目分配需跳过
  无生命周期的资源。
- access events 在 `build_resource_versions` 中按 pass 声明序追加，同一资源的写事件天然按声明序
  排列，可直接用于 producer 解析（对应原 Step B/C 的版本化语义，无需 packed version handle）。
- 注入的 UploadPass 位于 `passes[0]` 且 `backend_upload=true`；它只访问注入的 UploadArena buffer，
  必须无条件为根。
- `frame_plan` 的资源来源枚举：`persistent_buffer/persistent_image/transient_*/swapchain_image`
  （`render_device.h:311-318`）；persistent/swapchain 在 compiled rows 中 `is_imported=true`。
## 设计
### 活性根（root）规则
pass 满足任一条件即为根：
1. `backend_upload == true`（注入 UploadPass）；
2. 写 swapchain attachment（present 输出）；
3. 对 `is_imported` 资源（persistent/swapchain）有 write 或 read_write 访问（外部可见副作用）；
4. `frame_pass_row.side_effect == true`（新增显式标记，默认 false——纯追加的 ABI 扩展）。
### producer 闭包（忠实原 Step B/C/D 的版本化语义）
- 按资源收集写事件（声明序已有序）；活跃 pass P 读取资源 R 时，其 producer = 声明序在 P 之前
  最后一个写 R 的 pass；无 producer（imported 先读）则不展开。worklist 迭代至不动点。
- 只沿"读→生产者"反向传播；WAR/WAW 序边不保全活性（被剔除 pass 不存在即无冒险），与原设计一致。
### 新 phase：`cull_passes`
插入位置：`build_dependency_dag` 之后、`schedule_passes` 之前。
`compiler_state` 增加 `std::vector<uint8_t> active_passes`（`src/core/system.h`）。
`compiled_pass_row` 增加 `bool active = true;`（`include/render_graph/compiler.h`，自省/调试用）。
### 下游调整
- `core::schedule_passes`（`src/core/graph.cpp`，内部函数）：接收活跃集，Kahn 只在活跃子图上
  播种与减度；不完整排序仍报 `cycle_detected`。
- `compile_lifetimes`：统计 first/last 时跳过非活跃 pass 的事件；两个物理分配循环中，
  `first_order == max`（无生命周期）的资源 `continue`——`handle_to_physical_*` 保持
  `invalid_resource`，不产生 physical meta 与 memory block，backend 不做分配。
- `compile_synchronization` / `compile_submissions`：不改（活跃集经 `scheduled_passes` 传导）。
- `publish_compiled_plan`：`render_graph_statistics` 增加 `culled_pass_count`（hardening.h，
  纯追加），供测试与宿主观测。
### Backend（`src/backend/vulkan`）
预期零改动：`on_compile_resource_allocation` 遍历 physical 表（死资源无条目）；record 只走
`scheduled_passes`；`can_reuse_plan` 由 plan 内容确定性驱动。实施时核对 `vk_backend.h` 与
`dx12_backend.h` 的 allocation 路径不存在"按 logical 全量遍历"的假设；若有则补 `invalid` 容忍。

## 明确不做
- 层级 B（持久资源逻辑句柄化 / apply_resource_changes 惰性物化）不在本次范围。
- 不引入 frame pass 的运行时裁剪条件（如视锥裁剪驱动 pass 剔除）——culling 只按依赖闭包。
- 不改 `validate_recipe` 的"全量校验"行为（死 pass 的用法错误仍然报错，fail fast）。
