## 一、结论摘要

1. 现有 `resource_change_batch`（按操作类型分列的 9 span + 三阶段事务 + rollback）是
   提交流的正确形态，**不是 AoS 债务**；"统一 index 的 SoA + 按 index 并行"会破坏
   批次内依赖序（create → upload → bindless publish）与事务原子性，且并行收益不存在
   （create 撞 VMA/驱动锁，upload 是 memcpy 带宽墙，不随线程数变快）。
2. 几何路径"单目的地大 buffer + 单事务提交"是设计使然且正确（bindless ABI 下全几何
   一个 VkBuffer/一个 slot/一份生命周期）；G 级场景的真正卡点是**单事务的帧时间停顿
   （memcpy 墙）**，不是行形状。
3. 基准实测：合并行形状（单目的地 + region 列）只省全链 2–6%；行元数据占 payload 3%；
   大头是行构造与 memcpy。结论：行合并是"锦上添花"，但它买的终局提交 API 形态（见 §五.4）。
4. 落地顺序：可增长 arena 池 → 分块流式提交（同一 arena 跨帧续传）→ 专用传输线程 →
   合并行形状 / GPU 解压（终局）。

## 三、现状盘点

- 批次形状：9 个按操作类型的 span 列（`render_device.h:192-203`），行数据在调用方，
  payload 只引用不拷贝；消费为逐列遍历 + 结构化诊断 `{phase, row_kind, row_index}`。
- 三阶段事务：validate（逐行查表/范围检查）→ prepare（原生资源创建，失败 rollback
  全部已备资源）→ publish/commit（`vulkan_device.cpp:232-327`）；early-exit 是事务性
  而非缺陷，错误路径分支稳态不可预测性为零。
- 几何单目的地：主仓 gltf recipe 全部几何进 `state.geometry` 一个 arena
  （`gltf_render_recipe.cpp` geometry_capacity），切片偏移由 `plan_geometry_uploads`
  算出；`geometry_cursor` 天然支持跨帧续传（分块流式的基础）。
- 逐行成本构成：查表（小表）、范围检查（ALU）、memcpy（带宽墙）、`vmaFlushAllocation`。

## 四、大场景（G 级）成本模型

| 成本项 | 量级 | 性质 |
|---|---|---|
| 上传 memcpy（含 flush） | 1–3 s/GB | 带宽墙，物理下限 |
| 行元数据（2×32B + 16B/primitive） | 3% payload，几十 ms 构造 | 可优化（行合并） |
| validate 逐行查表 | ~10–20 ms/25 万行 | 可优化（查表去重/合并） |
| create | O(纹理数/arena 数) | 已摊销：大 arena 子分配，非逐 primitive |
| 解码 | 数秒级，异步 | 已在主仓 asset_service worker |
| **单事务阻塞帧** | **整个 1–3 s 挂起一帧** | 架构问题：分块流式解决 |

## 五、方向与落地顺序（每条含验收口径）

1. **可增长 arena 池**（主仓 recipe，小改）：按需开新 arena、句柄不变、切片逻辑不变；
   消除固定 256 MB 容量墙。验收：加载基准复测 + 契约测试绿。
2. **分块流式提交**：GB 资产按 N 帧分片 apply 到同一（或池内）arena，`geometry_cursor`
   跨帧续传；帧时间有界，加载进度可上报。验收：帧时间 p99 有界 + GPU smoke。
   ✅ 2026-08-16 已落地（主仓 M7，`e5cad5c8`）：运行时资产按每帧 8MB 字节预算分片
   （整 mesh 边界），片规划为纯函数 `plan_upload_chunk`；进度经 A0 协议
   `telemetry.load_progress` 逐片上报；验证 91.2MB 合成资产 13 片加载期间
   帧时间 p50/p99≈7ms 有界。T1/T2/T3（压缩/GPU 解压/DMA）仍按 §六 分级回退待后续。
3. **专用传输线程**：upload memcpy 出主线程（worker 解码 → transfer 上传 → 主线程注册）；
   主线程永不 memcpy GB 数据。验收：主线程帧时间不随加载抖动。
4. **合并行形状**（子仓 API 提案）：`{destination, span<byte_range> regions}` 行 +
   validate 查表去重；本仓变更走本仓治理。验收：加载基准对照（预期仅 2–6%，买终局形态）。
5. **终局：NVMe DMA + GPU 解压**：提交协议退化为区域描述符流；见 §七 跨平台现状。

## 六、能力检测与分级回退（落地必做）

DirectStorage / 厂商扩展不是处处可用（§七 跨平台现状），落地必须带**运行时能力检测 +
多级回退**，而不是硬编码单一路径。原则：**优先尝试最高级，检测失败逐级下落到仍完整可用
的层级；每一级都是独立可交付的正确路径，不是半成品降级。**

### 6.1 检测点（初始化时一次 + 加载时按资产复核）

| 检测点 | 方式 | 决定 |
|---|---|---|
| OS / 平台 | 编译期 + 运行时 | 是否具备 DirectStorage 候选资格（Windows 10/11） |
| API 扩展存在性 | `vkEnumerateDeviceExtensionProperties` / DS factory 创建 | T3 的 API 入口是否存在 |
| 驱动能力 | features/properties 查询（内存解压方法位、GDeflate 级别） | T3 是否可用，还是落到 T2 |
| 格式支持 | 按资产块查询压缩格式（GDeflate 级别 / zstd） | 逐资产选择解压层与压缩格式 |
| 存储介质 | 磁盘类型探测（NVMe vs SATA vs 网络盘） | T3 的 DMA 直通收益是否成立（SATA 上退化为普通 I/O） |

### 6.2 分级方案（T0–T3，每级完整可用）

| 级 | 路径 | 依赖 | 定位 |
|---|---|---|---|
| **T3 原生 DMA + GPU 解压** | DirectStorage / Vulkan vendor 扩展：NVMe → GPU，GPU 解压（GDeflate） | Windows + 驱动 + NVMe | 最优；CPU 全程不碰数据 |
| **T2 自研 GPU 解压** | CPU 异步读压缩块 → 压缩字节 memcpy（4–10× 变小）→ GPU compute 解压进 arena（`VK_EXT_memory_decompression` 或手写 compute） | 任意现代 Vulkan | API 无关的"准 T3"；memcpy 墙按压缩率塌缩 |
| **T1 CPU 解压就地写入**（"我们的优化版"兜底） | worker 线程异步读压缩块 → **CPU 解压直接写入 mapped 上传内存（单趟、无中间 staging 拷贝）** → 分片流式提交 | 仅 zstd + 普通 mapped buffer | 无厂商依赖；字节数 4–10×，帧时间分片有界 |
| **T0 裸分片 memcpy** | 无压缩、分片跨帧 memcpy 到同一 arena | 无 | 正确性兜底（如无压缩资产/超低端设备） |

关键认知：**分片 memcpy 只解决帧时间（摊平停顿），不减少总字节数**；T1 相对现状的收益
来自**压缩（字节数 4–10×）+ 就地解压（消灭二次拷贝）**，远大于行合并形状的 2–6%。
T1 应被视为默认第二方案，而不是把"更多线程的 memcpy"当第二方案。

### 6.3 决策流程

初始化：OS/平台 → API 扩展 → 驱动能力 → 得最高可用层级（记入 `capabilities` 行）。
加载时：按资产块做格式/介质复核，块级选择该资产的解压层；同一帧内不同资产可落不同层级。
遥测：每层级命中次数 + 每级吞吐（加载基准扩展口径），供线上调优与回退验证。

### 6.4 验收口径

- 每级路径均有加载基准数据（复用 `cglab.loading_benchmark` 扩展口径：含压缩率、解压、
  分片节奏）；
- 检测失败的组合（无扩展/非 NVMe/低端设备）逐一有测试锁定落到预期层级；
- GPU smoke：T0/T1 路径与现状渲染结果一致。

## 七、跨平台背景（DirectStorage 现状，2026-08 检索）

- **DirectStorage 是平台/API 专属技术**：Microsoft API（Windows 10/11 + DirectX 12），
  1.1 起支持 GPU 解压（GDeflate），宣称加载时间最多降约 40%；需要 GPU 厂商驱动支持
  （NVIDIA RTX IO / AMD / Intel）。采用仍属少数：首批如 Forspoken、Diablo IV，
  UE5 提供支持；详见 [The FPS Review](https://www.thefpsreview.com/2022/11/11/directstorage-1-1-is-out-now-and-can-reduce-load-times-by-up-to-forty-percent-in-supported-games/)、
  [TechSpot](https://www.techspot.com/news/99449-nvidia-rtx-io-finally-emerges-games-supporting-directstorage.html)。
- **Vulkan**：Khronos 已发布 `VK_EXT_memory_decompression`（内存解压扩展，见
  [vkdoc](https://vkdoc.net/extensions/VK_EXT_memory_decompression/)、[Khronos proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_memory_decompression.html)）；
  NVIDIA 另发布支持 RTX IO 加速的 Vulkan 扩展（Windows/Linux，见
  [Khronos News](https://www.khronos.org/news/archives/nvidia-ships-vulkan-extensions-to-support-accelerated-rtx-io-on-windows-and-linux)）；
  社区另有 Linux 侧 DirectStorage 风格运行时实验（[ds-runtime](https://github.com/infinityabundance/ds-runtime#1)）。
- **Metal**：无官方等价物；机制本身（PCIe DMA、GPU compute 解压）在硬件层可用，
  但需手写 compute 管线，无标准 API。
- **移动端（SoC 统一内存）**：同类问题基本消解——无 PCIe 边界、无独立显存，GPU 直读
  系统内存，"DMA 搬移"这一半不存在；解压这一半由 **ASTC/ETC2 等 GPU 原生压缩纹理格式**
  承担（磁盘直读、GPU 原生消费，无解压 pass）；流式加载 = 异步 I/O + 分块；瓶颈转向
  flash I/O 与内存带宽。
